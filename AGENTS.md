# AGENTS.md

Project instructions for AI coding agents working in this repository.

## Overview

A static single-page site: a curated catalog of films, series and documentaries about computers, technology and AI. No build step, no dependencies, no server. GitHub Pages just serves the repo root.

Run locally:

```bash
python -m http.server 8000
# then open http://localhost:8000
```

## Structure

- `index.html` — page markup, `<template id="tpl-catalog">` inline component template. Five blocks are GENERATED by `gen_pages.py` (edit via markers, never by hand): the theme head-script (`<!-- begin:theme-script -->` … `<!-- end:theme-script -->`), the static JSON-LD (`<!-- begin:index-ld -->` … `<!-- end:index-ld -->`), the no-JS catalog list (`<!-- begin:catalog-noscript -->` … `<!-- end:catalog-noscript -->`), the catalog-last-updated widget (`<!-- begin:last-updated -->` … `<!-- end:last-updated -->`) and the Yandex.Metrika snippet (`<!-- begin:metrika -->` … `<!-- end:metrika -->`, single source `gen_pages.METRIKA_SCRIPT`)
- `films/<imdbId>/index.html` — one static SEO page per record (generated; slug is `<id>-<title-en-slug>`, id falls back to `kp-<kpId>` when there is no imdbId). Each page embeds its own record + related titles as `window.FILM_PAGE` and does NOT load `js/data.js`
- `js/data.js` — the catalog (`window.CATALOG`, array of items, each with `desc.ru`/`desc.en`); single source of truth
- `js/catalog.js` — GENERATED by `tools/gen_pages.py` from `js/data.js`: same catalog without `desc` (main page doesn't need it); never edit by hand
- `js/i18n.js` — translations (`window.I18N`), keys for both `ru` and `en`
- `js/app.js` — Vue 3 app (global prod build in `js/vue.global.prod.js`), all filtering/sorting/i18n/theme logic
- `js/film.js` — Vue 3 film-page app (shared by all `films/*` pages; same lang/theme/i18n behavior as `app.js`, uses `window.FILM_PAGE`, does NOT load `js/data.js`)
- `js/common.js` — shared helpers (`window.ITMoviesCommon`): slug/URL builders, lang & theme resolution, rating formatting, storage wrappers, error handler (used by both `app.js` and `film.js`)
- `js/*.min.js` — GENERATED by `tools/gen_pages.py` (minified copies of `i18n.js`/`common.js`/`app.js`/`film.js`); the pages reference the `.min.js` files, never edit by hand
- `css/style.css` — all styling, wrapped in `@layer reset, tokens, base, components, utilities`; CSS variables for theming plus the spacing/radius/z-index/outline/container scale (see **CSS contract** below)
- `static/` — images, fonts, posters (`static/posters/*.webp`)
- `tools/` — local Python helper scripts (tracked in git):
  - `lib.py` — shared helpers (catalog/i18n/slug/genres parsing, `SITE_BASE`) used by the scripts below
  - `verify.py` — integrity checker (source of truth; verifies generated pages are fresh, theme/JSON-LD/noscript/metrika blocks are in sync, JS↔Python slug and related parity, `js/catalog.js` and `js/*.min.js` fresh, regenerates `sitemap.xml` and `robots.txt` only when stale, `--no-write` = check-only, `--strict` = missing Node fails the run, requires `.nojekyll`)
  - `gen_pages.py` — generates `films/*` pages from `js/data.js` + `js/i18n.js` (each embeds `window.FILM_PAGE` and the Yandex.Metrika snippet), generates `js/catalog.js` and `js/*.min.js`, and injects the theme, JSON-LD, no-JS, last-updated and Metrika blocks into `index.html` / `404.html` via markers
  - `gen_posters.py` - generates the poster variant ladder in `static/posters/`, first bringing any master taller than `lib.POSTER_MAX_HEIGHT` (600px) down to that height with the proportions kept, then re-encoding any master still >= 100KB under `TARGET_BYTES` **without ever destroying one it cannot reach** (idempotent; run after adding new posters - `tools/verify.py` checks every catalog poster has the whole ladder, all rungs at their rung width and at the source aspect ratio; the widths come from `lib.POSTER_VARIANT_WIDTHS`, never from a constant here)
  - `smoke.js` — node smoke harnesses (app.js / slug parity / film.js / related parity, each also run against `.min.js` via `--min`) driven by `verify.py`
  - `pw_kp.py` — Kinopoisk search + rating lookup via Playwright (kpId, kpRating, kpVotes, IMDb sub-rating)
  - `kp_votes.py` — bulk Kinopoisk vote-count collector over existing kpId values (resume via `_tmp/kp_votes.json`, `--limit`/`--reset-null`)
  - `poster_crop.py` — measures poster crop with no browser: both quantities (`PROXY = |w/h − 2/3|` and `DISCARDED_AREA = 1 − (bw/scale)(bh/scale)/(sw·sh)`, `scale = max(bw/sw, bh/sh)`) from real Pillow dimensions, prints median/p90/max for each, how many posters are exactly 2:3 and how many lose anything, the worst five by **each** quantity, and every poster over `DISCARDED_AREA_CEILING`. Runnable and importable (`--dir`, `--box W H`, `--ceiling`, `--json`, `--quiet`); exits 1 when the bound is exceeded, so `verify.py` block 4c calls it instead of re-deriving the arithmetic. **The library does not meet the bound: 54 of 155 posters. Since 2026-09-28 `verify.py` block 4c REPORTS that and no longer fails on it, by the human partner's ruling - this tool still exits 1, and the bound is still 0.02.** See the poster section below for why the gate was silenced and what it must never be read as.
  - `e2e.py` — optional real-browser smoke (Playwright + chromium, local only, NOT part of the verify gate): main-page filter/lang, film-page theme/share/related, bootstrap fallback. On the related cards it asserts the two things only a browser can see — the **rendered** `.rc-poster` box is 2:3, and the file `currentSrc` names is a real file on disk — and *reports* the discarded area of those files using `poster_crop.py` without gating on it. The old `POSTER_CROP_CEILING = 0.16` is gone; the bound belongs to `poster_crop.DISCARDED_AREA_CEILING` — see the poster section
  - `show_types.py` — prints every record with its line number in `js/data.js`

## CSS contract

`css/style.css` is the only stylesheet and it is wrapped in cascade layers. These rules are a contract, not a report; the full Stage 2a record (all **57** tokens as of that stage, layer rule counts, every sanctioned literal — **that count is the spec's, not the tree's**; the tree is at 61 and the gate prints the live number every run) is `docs/superpowers/specs/2026-09-26-ui-redesign-design.md` §8, and the Stage 2b record is §9 of the same file — but that path is **gitignored**, so this section is the copy that ships.

- **Layer order is `reset, tokens, base, components, utilities`**, declared in one ordered statement on line 1. Put a new rule in the layer it belongs to. Never append unlayered: an unlayered rule outranks every layered one, so one stray block silently defeats the whole system.
- **Tokens, not literals.** Spacing is `--space-1`…`--space-9` plus `--space-0-2`/`--space-0-35`/`--space-1-25`/`--space-2-25`/`--tap`; radius is `--radius-xs|s|m|l|xl|circle`; stacking is `--z-raised`/`--z-modal`/`--z-skip`. **61 tokens are declared and all 61 are referenced** — do not add a token you do not use, and do not inline a value a token already carries. (`--space-9: 4.5rem` is the 72px section rhythm added by the 2026-09-29 dark editorial redesign; measured on that tree: 100 declarations, 58 unique, 58 referenced, 0 orphans. The count was 60 after `--logo` was deleted twice, `--radius-pill` once and `--accent-text` once, and is **61** since 2026-09-30 added `--on-media: #ffffff` for the featured card's text on the poster scrim. **`--on-media` is a new value, not a second name:** `--ink` is `#f7f8f8` in dark and near-black in light, `--focus` is `#f2eee8`, and a value that had to be white in BOTH themes is the one thing none of them is — `--ink` is invisible on the black scrim in the light theme, which is the whole reason the token exists. Do not repoint the scrim's text at `--ink`. It is not a duplicate and `check_token_lifecycle()`'s lack of a duplicate-value rule is not licence to add one.)
- **`--radius-pill` was deleted, not redefined, and that is the second instance of the same rule.** The partner asked for it to be made small — 6px. `--radius-s` **already is 6px**, and `--radius-pill` had exactly one consumer, `.rating-chip` (`.rating-chip` was the only fully rounded thing left on the site; `--radius-circle` at `50%` is the real circle and is used 3×). So `6px` was not a new value, it was a **second name for `--radius-s`**, which is exactly the condition that got `--icon` deleted earlier in this project. The fix is the token, and the token was `--radius-s`: the single usage now reads `var(--radius-s)` and the declaration is gone — **pixel-identical to the request, 63 → 62 tokens.** (60 after the 2026-09-30 header ruling, which took `--accent-text` with it — see the bullet below.) **Do not re-add it to make a chip look pill-shaped**; if a genuinely large radius is ever needed, add it as a *new distinct* value on the scale (`--radius-2xl`, say) rather than as a second name for an existing one. `check_token_lifecycle()` checks orphans only and has **no duplicate-value rule**, so a redefined token that collides with another would pass the gate silently — the discipline here is the thing doing the work, not the gate.
- **`--accent-text` is the third token this project has deleted for having a single consumer, and its consumer was the nav marker, so its death is a by-product of the 2026-09-30 ruling rather than a separate decision.** It was not decoration: it exists because of finding **I9**, which measured `--accent` used as *text* at **4.21:1 dark / 4.34:1 light** and added a theme-specific lighter/darker value of the same hue to reach **6.47:1 / 6.40:1** (`--accent` is `#5e6ad2` in both themes, so the fix is a value, not a hue). The only text it ever painted was `.nav a[aria-current="true"]`, and that rule went with the marker. **Five `color: var(--accent)` uses remain and none of them is body text:** `svg:not(.heart)` and `.share-btn[data-net="native"]:hover .share-ico` (icons, judged under 1.4.11 and measured → below), `.fav-filter.active` (its `currentColor` reaches an `<svg>` child), and two **glyphs** — `th.is-asc/.is-desc .arrow` and `.mobile-sort .arrow` (`↕`). **The third glyph, `.featured-star` (`★`), left this list on 2026-09-30 and is the worked example of why the ban below is a ban and not a preference:** the `4.21:1` figure quoted above was measured on a flat `--surface-1`, and the 2026-09-30 rework put the star on a photographic scrim, where that measurement does not exist. Re-measured there — 6 widths × 2 themes, worst-pixel against the real composited scrim — `--accent` read **2.81–3.34:1 (mostly ~2.9)**, under the **3:1** floor 1.4.11 sets for graphics, so the glyph now **inherits `--on-media` from `.featured-card-meta`** and carries no rule of its own. The colour was ruled on twice, and it still changed: a ruling made against a surface that no longer exists is not a ruling about the new one, and the fix here is the only one that needed no new token. **Do not re-add `--accent-text` to darken the two arrow glyphs**, and do not repaint the star: `check_token_lifecycle()` checks orphans only, so a re-declared token would pass every gate while quietly reintroducing a contrast finding that was already settled. If the arrows ever need to clear **4.5:1 for text** rather than **3:1 for graphics**, that is a new measurement and a partner conversation, not a token restore.
- **`verify.py` block 6d caps that, and it compares by value, not by text.** `STYLE_LITERAL_CEILING = {"spacing": 6, "radius": 0, "z-index": 0}` with `STYLE_LITERAL_SCOPE = {"spacing": "token", "radius": "any", "z-index": "any"}`. Every value is resolved to px and compared against token values resolved to px, so `12px` and `0.75rem` are caught as the same regression. A bare length in a box-spacing property (`margin*`, `padding*`, `gap*`, `inset*`, `scroll-margin*`, `scroll-padding*`, `top`/`right`/`bottom`/`left`), in `border-radius`, or in `z-index` fails the gate; a `calc()`/`min()`/`max()` of constant lengths is resolved and compared too, and a `clamp()` with a viewport term is not, because it is not constant. Use `var(--token)`.
- **The `radius` and `z-index` ceilings are absolute 0 and must never be raised.** Their scales are closed: all 6 radii in circulation are tokenised (`--radius-xs|s|m|l|xl|circle` — `--radius-pill` was the 7th and was deleted on 2026-09-30), and there are exactly 3 z-index tokens and exactly 3 uses. Any bare value in either family means a *token is missing*, and the fix is the token. The `spacing` scale is open — `0.1em` badge padding, `15vh` boot centring, `-50px`, `-6px` are legitimate and no token can or should cover them — so spacing keeps a real ceiling, currently **6**: `4px` ×2 (`--space-1`) and `8px` ×4 (`--space-2`), all px-vs-rem and therefore equal only at a 16px root. Those 6 and the 25 off-scale values are named on every run; a new one must be tokenised, or the ceiling raised in the same change, with its name and reason. The `rem` base is the root `font-size`: `verify.py` reads it from `css/style.css`, falls back to the CSS initial value, and prints which on every run. Box sizing (`width`, `height`, `min-*`, `max-*`, `flex-basis`) is not tokenised at all and is outside the gate.
- **There is one canonical breakpoint scale — `xs ≤575 / sm ≥576 / md ≥768 / lg ≥1024 / xl ≥1200` — and it is written in exactly one place: `lib.BREAKPOINT_SCALE = (575, 576, 768, 1024, 1200)`.** The px values a `@media` condition may use are **`lib.CSS_MEDIA_EDGES`, which is derived from that tuple, not listed beside it**: every boundary, plus every boundary minus one for the `max-width` form that expresses "below the next tier" — so `{574, 575, 576, 767, 768, 1023, 1024, 1199, 1200}`. Deriving it is the point: a hand-listed set silently omitted `576` once, which meant the gate rejected a correct `sm`-tier rule while offering "add it to `lib.CSS_MEDIA_EDGES`" as the remedy — i.e. telling you to edit a constant that exists to be derived. **`verify.py` 6f now checks the relationship instead of trusting it**, and fails if `CSS_MEDIA_EDGES` is not a superset of `BREAKPOINT_SCALE`, or if `BELOW_MD_MAX` (the poster `sizes` breakpoint, itself derived as `BREAKPOINT_SCALE[2] - 1`) is not an admitted edge. The poster `sizes` value is the single source `lib.poster_sizes()`, feeding 308 generated occurrences. `verify.py` enforces the whole chain: **6e** polices the emitted `sizes` values against `lib.poster_sizes()` (the condition *and* the slot sizes), and **6f** parses every `@media` and `@container` prelude in the stylesheets named in `verify.CSS_MEDIA_FILES` and asserts the width edges it finds are a **subset** of `CSS_MEDIA_EDGES`, reporting every value found and every value rejected. Two properties of 6f are deliberate and must not be "tidied": the relation is a **subset, not equality** — 1024 and 1200 are permitted while unused because Stage 3 adds the `lg` and `xl` tiers, and a gate that must be edited before a legitimate tier can be added is a gate that gets edited carelessly; and its scope is **the stylesheet, not the repository** — a bare 480 or 950 is equally at home in prose (this file, the gitignored spec) and in an SVG path (`static/share.svg`), so a repo-scoped gate would report violations in files that are already correct and its own remedy ("add the value to `lib.CSS_MEDIA_EDGES`") would not apply to them at all. To use a value that is missing on purpose, add a boundary to `lib.BREAKPOINT_SCALE` — never to `CSS_MEDIA_EDGES` and never to 6f. A rejected edge's own failure message says the same thing, and it is worth reading: a gate that names the wrong file as the remedy teaches the wrong lesson.
- **6f also pins three things a re-key must not disturb,** and each carries its reason in the failure message: exactly one `@media (prefers-color-scheme: dark)` and exactly one `@media (prefers-reduced-motion: reduce)`; exactly one `@container scroll-state(scrollable: top)` **with its original condition** — it is a container query, not a width query, so any tool that re-keys "all breakpoints" must leave it alone and this is what proves it did; and **the separate blocks carrying `max-width: 575px` — two of them since 2026-09-29, three before that, pinned by count at `verify.CSS_MEDIA_XS_BLOCKS`**. It also refuses a width edge in any unit it cannot resolve to px (`60em`), because a width nothing in the project can check is a width nothing checks.
- **There are two `max-width: 575px` blocks, three until 2026-09-29, and merging the survivors is still a layout change, not tidying.** The survivors carry `.menu-toggle`/`.featured-grid` (the carousel; first statement at `:1625`) and `.profile` (`:2349`); the third, `.related ul`, is gone. It held `grid-auto-columns: minmax(200px, 82%)`, and 200px was the demotion that left the related card's text column **61.2px** at every width ≤ 575 — poster 104 + padding 24 + gap 8.8 inside a 200px card. It was **deleted, not merged and not edited**: the `≤767` rule already carries `minmax(240px, 75%)`, and a track of that shape measures **240px at 320 as well** (measured — the min governs even when the max sits below it), so an xs rule surviving only to hold a different `max` would be inert, and a dead block kept alive to pin a count is worse than a count moved for a reason. `verify.CSS_MEDIA_XS_BLOCKS` went 3 → 2 in the same change, and the control that proves the pin is live is putting 3 back: 6f then fails with `carries the xs edge max-width: 575px in 2 block(s) (:1625 .menu-toggle {, :2349 .profile {), expected 3` (run 2026-09-29, exit 1, constant restored). `480` and `525` both collapse onto `575`, and **media conditions cannot read a custom property**, so the spec's "emit each boundary once" is realised as a canonical value set plus a gate rather than as one definition; there is no way to write the condition once. Merging a survivor moves rules across the stylesheet, and Stage 2a deliberately kept every media query on its original line precisely so that source order could not shift. A single xs block, or a third one, is a deliberate decision recorded in the spec, and `verify.CSS_MEDIA_XS_BLOCKS` changes with it.
- **The retired edges `480 / 525 / 720 / 721 / 950` do not exist in `css/style.css` and must not come back.** A retired edge could otherwise be reintroduced one literal at a time with every other check green, since 6d examines only box-spacing properties and 6e only the `sizes` attribute. 6f closes that. A mention of a retired edge in prose is not a violation — 6f parses preludes, it does not grep text — but prose must mark it as retired so the next reader does not take it for a live condition.
- **There is a 1 CSS px seam in the viewport axis and it is not a bug you can gate away.** The conditions tile **every integer width** 0–1500 with no gap and no overlap, but the open interval **(767, 768)** matches no width block — **1.00 CSS px** wide, arithmetically, in the re-keyed tree and in the pre-re-key tree alike, which had the identical seam at (720, 721). It is unreachable from every harness in this project: **Playwright refuses a fractional emulated viewport outright** (`Browser.setWindowBounds: Invalid parameters`, on both `new_context` and `set_viewport_size`), so no probe here can ask the question. **Which way a browser rounds a genuinely fractional viewport is not established by this project and is not claimed** — one earlier note said "truncated (measured: 720.5 → 720)" and that measurement was reading its own `int(w)`; another said the opposite direction. If you want the direction, you need a probe that can express a fractional width at all. 6f prints the seam as **information, not as a failure**, and says why: a gate asserting perfect tiling would fail on a property CSS does not have, and it would fail on a correct stylesheet.
- **The related card `.rc` has exactly ONE hand-maintained source, `gen_pages.RC_CARD` in `tools/gen_pages.py`, and it is a Vue template, not a static fragment.** `gen_pages.render()` produces two renderings of it and both are what the page ships: the no-JS card in `<noscript>`, resolved by `rc_card_html()` through `rc_values()`, whose `RC_STATIC` table is keyed by the *exact expression text* the template binds (`relatedTitle(r)`, `hasRating(r.kpRating)`, `t.kpShort`, …); and the client card, emitted verbatim into every film page as `window.FILM_RC_CARD = "<escaped template>"`, which `js/film.js` splices into `FILM_TEMPLATE` as `${RC_CARD}`. **The client keeps owning every value it displays** — what crosses into the page is a template with `{{ }}` and `:` bindings in it, never interpolated text — so switching a film page to `en` still re-renders the card in English; that is measured, not assumed. The table and the template **close on each other**: an expression `RC_CARD` binds that `RC_STATIC` has no value for, or a `RC_STATIC` entry the template no longer binds, raises out of the generator rather than letting one side fall back to a value of its own. Edit the card in `RC_CARD` and re-run `python tools\gen_pages.py`; never hand-edit a card in `js/film.js` (that file no longer has one) and never hand-edit `window.FILM_RC_CARD` in a committed page.
- **`verify.py` 6g compares the MARKUP of those two renderings, and it is blind to the source by construction — read it as "the two renderings of this source agree", never as "this card is correct".** Both sides are rendered **in memory** from one `gen_pages.render()` call, the client side decoded out of the same string with `json.JSONDecoder().raw_decode`, so nothing here reads a committed `films/*/index.html`: that is deliberate, and it is the only thing in the project that can see a generator-side change (a deleted element, a broken renderer, a mangled emission), where reading the pages would leave 6g green and leave only the freshness check to notice. It compares depth-first `(tag, classes, parent-index)` lists — same nine nodes, same classes, same nesting — and no attribute *value* participates. **What one source costs is the other half of the old gate: a change made in `RC_CARD` moves both renderings at once and is invisible to 6g, and no gate over a single source can see it, because the source is exactly what 6g treats as the truth.** Three checks cover the ways that can go wrong quietly, all inside 6g: a second copy of `<a class="rc"` in any hand-maintained file is an error (`RELATED_CARD_SOURCE_SCOPE`, which is why a card pasted back into `js/film.js` fails); Cyrillic anywhere in the client card is an error, because a literal is Russian whatever `lang` says; and every class the card puts on an element must exist in `css/style.css`, which is the one file that did not come out of `RC_CARD` and is therefore the only independent witness left that the card and its styling still meet. A class renamed in `RC_CARD` used to be caught by the two-copy comparison and is caught now only by that last one.
- **`.featured-card` on the main page and `.rc` on a film page are INTENTIONALLY two different cards. Do not unify them as a cleanup.** Measured inventories: `.featured-card` (the `<a class="featured-card">` in `index.html`'s featured template — line numbers drift, grep the selector) has an accent top border, its own title with an alt-title line under it, a `★` + year and a first-genre row **painted on a scrim over a full-bleed poster**, and a **six-column grid above lg / a 156px rail below it**; `.rc` has none of those. The spec's §1.4 property table records that *every* compared property differed as of that stage, and it is the reference for that claim; **the 2026-09-30 rework below widened the gap rather than closing it** — `.rc` still puts its poster on top with the text beneath it and carries no scrim, no `--on-media` and no `★`. Merging them is a visible design change on the main page and on 154 film pages, it was explicitly declined, and it belongs with the Stage 3 work that owns the featured block, the table and the grids. The parity gate covers `.rc` only and is not evidence about `.featured-card`; their divergence is the intended state, not an unclosed gap.
- **The 2026-09-29 featured-card rework shipped the approved design — six cards (2+2+2), an alt-title line, `★` instead of the badge, a 70px poster column — and the hole under a one-line title is gone, fixed by deleting `min-height: 2.5em` rather than by any padding trick. Keep the rest — the alt row, the `★`, the deleted `min-height`, the pick count.** The card then read title / alt / (`★` + year, first genre) / ratings. The partner re-placed the source and the tool ran again, which is how the invariant was found. **Two fixes, and the second is the one that matters:** `squeeze()` now encodes to a **temporary file** and moves it into place only if it reaches the target, so a master that cannot be squeezed is left **byte-identical** and reported by name — a size policy is not a correctness property, and losing the master to enforce a byte count on an asset the ladder never uses at full size is the wrong trade in both directions; and `normalise_height()` brings an oversized master down to 600 **before** the byte target is even considered, which makes that target reachable in practice and means the destructive path is never entered for a well-formed asset. **The general lesson, and it is the same shape as every other dead-declaration record in this file: a tool that edits an asset in place and then fails has already spent the thing it was protecting.** Rescaling is a single Lanczos pass from the pixels **as placed**, not a downscale of an already-reduced file, and the ladder is then cut from the rescaled master — which is strictly better than cutting it from a squeezed one. ## The xs menu: a native `<dialog>`, and the no-JS tier that keeps the anchors

- **The xs navigation is a native `<dialog>` opened with `showModal()`, and it is the only navigation affordance below 576px. Above it, the inline anchor row is the affordance.** One source each: the button is `button.menu-toggle` in `index.html`'s `.tool-buttons`, and the panel is `dialog#nav-dialog` containing `nav.nav.nav--dialog`. The dialog is opened by `app.js`'s `openMenu()`/`closeMenu()` and nothing else — **there is no keydown handler for Esc and no hand-rolled focus trap, because `showModal()` provides the trap, the inertness of the document behind, and Esc.** Do not add either. The one handler that does exist is a `close` listener that syncs `aria-expanded`, because Esc bypasses the app entirely.
- **The nav's three anchors are rendered TWICE in `index.html` — once inline and once inside the dialog — and that duplication is the price of the no-JS guarantee, not an oversight.** The inline copy is `nav.nav:not(.nav--dialog)`; the dialog copy is `nav.nav--dialog`. They are the same three `#`-targets, so with JS on and no-JS both, the page holds two nav landmarks. Only one is ever rendered at a time, which is what `test_nav_tier` asserts.
- **The tier is expressed with `html:not(.js)`, and that is the whole no-JS mechanism.** `index.html:6` runs `document.documentElement.classList.add("js")` from an inline `<head>` script, so `html:not(.js)` is exactly "scripting is unavailable" and needs no JS of its own to evaluate. In the `max-width: 575px` block: `html:not(.js) .menu-toggle { display: none }` and `html:not(.js) .nav:not(.nav--dialog) { display: flex }`. **Measured consequence, and it is the reason this is not a silent trade:** with JS disabled the burger is `hidden` and the inline row renders with all three anchors at **every** width 320–1280. Without those two rules a reader without JavaScript gets a burger that cannot open, and the nav is gone. Deleting them is caught — see the mutation below.
- **The defect this replaced was real but narrower than "the xs tier", and the wrap band is locale-dependent.** The three anchors are 44px tall and `flex-wrap: wrap`, so the third wraps to a second row and is orphaned alone. Measured at every integer width 300–600, both locales, JS on: **`ru` wraps at 305–496 and is one row at 497+; `en` wraps at 300–444 and is one row at 445+.** At 375 both locales are 2 rows with the third anchor (`Документальные 53` / `Documentaries 53`) orphaned — the plan's claim, confirmed — **but the nav is already a clean single row at 520 and 575, which are also `xs`.** So 50px–100px of the xs tier was never broken, and the burger now covers it anyway. That is the accepted cost of a tier boundary at 576 and is stated here so it is not rediscovered as a bug.
- **Without JS the three nav anchors are present, focusable, and already dead: their targets are zero-height.** Each `#movies`/`#series`/`#documentaries` is a `<catalog-table>` custom element that Vue never renders without JS, so with scripting off each measures `0x0` with `childElementCount: 0`, and clicking one sets `location.hash` and scrolls to a zero-height point. The no-JS path that actually works is the generated `<noscript class="no-js-catalog">` list of 154 real film links. **So the xs no-JS nav was three links to nowhere before this change and is three links to nowhere after it — what changed is that they are no longer hidden behind a control that cannot open.** Fixing those targets is out of scope and is not a regression introduced here.
- **The xs page is shorter because the second row is gone, and it is shorter by a different amount per width.** Measured document height, 3 loads each, JS on: **11211 at 375, 11057 at 520, 11039 at 550, 11025 at 575** (spread 0 across loads at every xs width, because the removed row is not `Math.random`-dependent), against 11604–11613 at 576, 12456 at 768, 12044–12062 at 1024, 12003 at 1280. The 576/1024 spreads are the featured-shuffle noise, not this change. **At xs the nav's 2-row 96px box plus the burger's 44px is a net loss of roughly one row; above xs the inline row is unchanged.**
- **`aria-current` is GONE from the catalog nav, and it is gone because the partner ruled it gone (2026-09-30): "aria-current убрать, все равно не работает и непонятно зачем нужен".** The mechanism behind it took three bugs to reach zero, and the third is the reason it was not worth a fourth attempt. In order: (1) **one `IntersectionObserver` named the section occupying a band 20%–30% down the viewport** (`rootMargin: "-20% 0px -70% 0px"`, `threshold: 0`), picking the first of the three targets in the band and **deliberately leaving the previous value alone when the band was empty**. That read correctly — measured at 1280 over a 50px sweep, flips at 550 / 5500 / 7850 against geometry-predicted 598 / 5513 / 7853 — and the deliberate non-update is what made it *feel* sticky: scroll back above the first section and the band is empty, so `aria-current` stayed on `#movies` forever. Measured directly: `scrollTo(0,0)`, `Home` and a wheel gesture each left `marked=['#movies']` with **not one section in the band**. (2) A click was overwritten by the observer at **214 ms** on a `0 → 5436` smooth scroll that runs ~700 ms, and for most of that travel `#movies` genuinely *was* the section in the band — the observer was right and the click was right, and they disagreed for as long as the scroll took. `goSection()` + `sectionLock` (cap `SECTION_LOCK_CAP = 1500`, released by `wheel`/`touchstart`/`keydown` or the cap) fixed that, and `marker wrong after the click: 0` over a 961-width × 2-target sweep. (3) The latch survived all of it, because a scroll indicator has no state for "above all sections". **That is the structural defect, and it is why the fix is removal rather than a fourth rule:** a band observer answers "which section is in this strip", never "which section am I in". A mechanism that must represent the top of the page as a non-answer will represent it wrongly. **What was deleted:** `currentSection`, `watchCurrentSection()`, `goSection()`, `sectionLock` / `SECTION_LOCK_CAP` / `releaseSectionLock`, `cleanupSection`, the `:aria-current` binding on all **six** anchors in `index.html` (three inline, three in the xs dialog — both copies, or one copy would keep setting it) and the rule `.nav a[aria-current="true"]`. **What is deliberately NOT a global ban:** `js/film.js` still binds `aria-current` on the **related-rail pagination dots**, where it is correct — it names which page of the rail you are on, a position the reader chose by clicking, and the empty-band problem does not exist. `verify.py` **6i.3** therefore scans `index.html`, `js/app.js` and `js/app.min.js` only, and matches `aria-current` followed by `=` and a quote so the prose in `app.js` naming the mechanism does not trip it. **The history is kept in a comment block in `js/app.js`**, because the next reader who wants a section indicator will otherwise reinvent the band observer and hit the latch.

- **The xs-menu controls were measured against the 44px tap target and all of them clear it.** `.menu-toggle` and `.nav-dialog-close` are **44x44** and `.nav--dialog a` is **44 tall** at 320/375/575 (JS on), so none of them falls below the target, and the xs inline row is `display: none` and contributes nothing there. The six `.nav a is 99/101/107/109/157/165 x40` lines are the **desktop** inline row. If a future change makes the burger smaller than 44px, that is a regression.
- **`test_nav_tier` in `tools/e2e.py` is the guard for this whole mechanism, and both mutations are caught by it.** Scenario 12 of 12. It asserts, at 320/375/575/576/768/1280, that **exactly one** navigation affordance is reachable (`burger XOR inline`, never both, never neither), that the xs burger carries `aria-expanded="false"` when closed plus `aria-haspopup="dialog"`, `aria-controls` and an accessible name, that the dialog is a real `:modal` that takes focus, that **no focusable control outside it ever receives focus across a full Tab cycle**, that Esc closes it and returns focus to the burger, and — in a **second browser context with `java_script_enabled=False`**, the first in this project — that the burger is absent and the inline row still carries all three anchors at every xs width. Two mutations, both printed before their verdict was read, both restored with the blob re-checked (`ce92ebc7…` before, `6bfcfc5f…` after): moving the xs rules to `max-width: 767px` → `FAIL test_nav_tier: @576: above xs the inline row is the affordance` (and `test_featured_breakpoints` also fails, correctly); deleting the two `html:not(.js)` rules → `FAIL test_nav_tier: @320 without JS: the burger cannot work, so it must not be shown`. **The second is the one that matters: it is the no-JS regression, and it is loud.**

## The header: the sticky rule is gone, and the mechanisms that outlived it

- **The header no longer sticks, and the partner ruled it off (2026-09-30): "Sticky шапку, nav или что это прилипшее убрать совсем, не нужна". `position: sticky` was the ONLY one in the project, on `.top`; the nav lives inside `.top`, so the ruling was read as removing stickiness from the header, and the nav stays as ordinary content.** Removing it took a mechanism with it, because every part of that mechanism existed only to clear a sticky header. **Deleted, together:** `html { scroll-padding-top: var(--header-offset) }` and the token `--header-offset: 5rem` (its no-JS fallback), `trackHeaderOffset()` + its `ResizeObserver` + `cleanupHeader` in `js/app.js`, `.top`'s `z-index`, its `backdrop-filter` and its `--glass` background, and `verify.py`'s `HEADER_OFFSET_WRITER` gate. **`.top` became `background: var(--surface-1)`, opaque — and that was one commit too many: the panel itself is gone too, see the bullet below.** **What is kept and why:** the anchors and `scroll-behavior: smooth` — a nav that jumps instantly is a worse change than a header that scrolls away — and only `index.html` has in-page nav targets, so no other page was touched.
- **The `--header-offset` machinery is worth reading as a whole, because it is the most expensive thing this project ever built for a layout, and the cost is what makes the removal obvious in hindsight.** The header's height is **content-driven** and took **six distinct values** between 320 and 1280 (swept at every integer width, `_tmp/probe_header_facts.py`): **290** at 320–336, **214** at 337–364, **190** at 365–449, **185** at 450–767, **181** at 768–947, **117** at 948–1280 — the control row wraps to two lines below 365 and to three at 320–336, and the nav and the result count stop sharing a line at their own widths. The property needed a value at every width, so it was written from JS: `trackHeaderOffset()` read `header.top`'s box through a **`ResizeObserver`** (not a resize listener, because **a style change fires neither `resize` nor `scroll`** — the same reason `measureRail` re-measures on mount *and* on resize) and set `--header-offset` on the root, and the `5rem` in `:root` was the no-JS fallback. **A fixed per-tier token could not replace the measured write, and that was measured rather than argued:** a `5rem` = 80px constant is the header's height at **no width at all** — the counterfactual is short at **961 of 961** widths, worst **+210px at 320**, best **+37px at 948**, so it is the same defect as having no `scroll-padding-top`, only smaller, and there is no band where the constant happens to be right. **Do not restore the older numbers 264 / 242 / 190 / 166 / 142 / 138 / 80 / 74, or the phrase "80px is the header's height only at ≥1024"**: those were measured on the tree with the 32px logo and the 76px-wide `.theme-toggle`, and the logo is back at 100×100 and the buttons at 40px, so on that tree the short-header ceiling is 117 and the claim is false. **Two measurements from that era are historical and must not be quoted as current behaviour:** the "+22px offset jump when the web font swaps" reading was a probe that settled on a transient, and on the tree as it stood it measured **+0px at all eight widths** with one distinct value each. And the 961-width × 2-target sweep that justified the lock (`marker wrong after the click: 0`) also reported `section behind the header: 483` — on a **sub-pixel** criterion, worst **0.50px**, so even at its worst the offset was clearing a rounding error, not hiding a section.
- **`verify.py` 6i is the INVERTED gate for the removal, and the inversion is the point worth reading.** 6i.1 asserts `.top` is not sticky, 6i.2 asserts `scroll-padding-top` and any `--header-offset` write are gone, 6i.3 asserts nothing sets `aria-current` on the main page. **The gate it replaced asserted the opposite** — that something writes `--header-offset` and that `scroll-padding-top` exists — so **a check that fails when the old mechanism is missing and passes when it is present is a check that has to be deleted in order to make the ruling.** That is the wrong order of events, and it is the whole reason 6i asserts absence. Three scoping decisions inside it are deliberate and must not be "tidied": **6i.1 matches the `.top` selector as a whole selector part**, so `.scroll-top` (a legitimately fixed button) is not caught by a substring and a future legitimate sticky element does not need the gate edited first; **6i.1 also fails when it matches ZERO `.top` rules**, because a gate that matches nothing is green for the wrong reason — and it was not hypothetical: the first version of `_rule_bodies()` stepped *over* at-rule bodies instead of descending into them, and because the sheet opens with `@layer reset, tokens, base, components, utilities;` followed by five `@layer X {` blocks, **every real rule in the file lives inside one of them**, so the parser found 0 rules and 6i.1 was silently vacuous. That guard is what turned it into a loud failure. **6i runs `blank_css_comments()` first**, so the CSS comment explaining why the declarations are gone does not trip the check that says they are gone — a gate that greps raw text ends up getting its own documentation deleted. And 6i is placed **after `check_media_conditions()`** rather than where the old check lived, because that is where `blank_css_comments()` is defined.
- **6i.4 guards the header panel, and it protects the INVARIANT rather than the syntax: `background: none` and `background-color: transparent` also pass.** What is banned is putting ink behind the header, so any painting shorthand value and any `background-image:` fails. It scans **every** `.top` rule *including* the `@media` copies, because a panel that appears at one width is still a panel at that width. **Six mutations, each read back off disk before its verdict was read, with the pre-run hash re-checked after every restore — and re-read that hash rather than trusting this line, because the tree has since grown the A/B numbers in the comment above (it is `7B03896F…` today):** panel back into the base rule → `.top paints a background again`; `background: none` → passes; `background-color: transparent` → passes; `background-image: radial-gradient(...)` → fails; a panel added only inside the `≤767` block → fails; base rule deleted outright → 6i.1's guard fires.
- **The 6i.1 zero-match guard was UPGRADED for a reason worth the whole paragraph, because it was found by breaking the stylesheet by accident.** The first guard asked "did any `.top` rule match" — and `.top` has **three**: the base one and one in each of the `≤767` and `768–1023` blocks. While a CSS comment was being written with its opening `/*` missing, a block of prose sat **bare** in the stylesheet, which CSS reads as a qualified rule: its prelude runs to the next `{`, so **`.top`'s entire declaration block was re-parented under a selector made of English sentences and the base rule ceased to exist.** The guard counted the two `@media` copies and stayed silent. **`_rule_bodies()` therefore returns a third element — the enclosing at-rule path — and the guard now demands a `.top` rule whose path contains no `@media`/`@container`/`@supports`,** with `@layer` deliberately **not** treated as conditional, since it wraps every rule in this sheet and treating it as one would reject everything. The three `.top` rules now read as **1 unconditional + 2 conditional**. **Do not collapse that back to a plain count;** a guard satisfiable by a conditional copy cannot notice the unconditional one is gone. The damage was measurable, not theoretical: the header rendered **1225×144** instead of **1225×121** — 23px taller, with `display: flex`, `gap`, `padding-bottom` and `border-bottom` all gone — and **`verify.py` and all 16 e2e scenarios passed on it**, because no e2e test asserts the header's own layout (`test_header_controls` measures `.tool-buttons`; `test_nav_lands_at_top` only asserts the header's bottom is above the target's top, which a *taller* header satisfies). `css/style.css` is the only witness that the base rule exists, which is exactly why the guard now insists on an unconditional one. **The general form: a CSS comment's opening `/*` is load-bearing, and dropping it fails silently in every direction at once** — `blank_css_comments()` can no longer blank it, the parser reads the prose as a selector, and every gate that greps for the thing it just deleted starts matching the documentation instead.
- **`test_nav_lands_clear` became `test_nav_lands_at_top`, and the assertion flipped rather than shrank.** Its old job was "the marker lands correctly" and "the section lands below the sticky header"; both are gone, and the replacement is a **stronger** statement of the new state: with no sticky header a nav target has **nothing to hide under and must land at the top of the viewport** (asserted as `|sectionTop| <= 2`), and the header's bottom must sit **above** the target's top, which is the direct assertion for the sticky removal. **A surviving `scroll-padding-top` therefore fails this test even though nothing about the marker does**, which is the point: the removal is guarded from the CSS side, not only from the JS side. It reads `aria-current` across **both** nav copies, not only the visible ones, because below xs the inline row is `display: none` and a visible-only read would report a clean sheet on a page that still sets the attribute. **Two mutations, both printed before their verdict was read, both restored with the hash re-checked** (`css/style.css` `51F25F60…` before and after, `index.html` `47B8E0A6…` before and after): re-adding `position: sticky; top: 0` to `.top` → `FAIL test_nav_lands_at_top: @320: the header's bottom is 290.0 and #series's top is -0.3 -- the header is still covering the target, so it is still sticky` (and `verify.py` 6i.1 fails with `.top is sticky again`); re-adding `aria-current="false"` to one `#movies` anchor → `FAIL test_nav_lands_at_top: @320: after clicking #series these nav anchors still carry aria-current: ['#movies=false']` (and 6i.3 fails).
- **One defect in that test was in the harness, and it is worth recording because the old test could not have caught it: `scroll-behavior: smooth` makes a scroll in flight swallow the next fragment navigation.** `test_nav_lands_at_top` resets with `window.scrollTo(0, 0)` between targets, which is **smooth** under this stylesheet, so the click for the next target arrived mid-animation and was dropped: `scrollY` stayed at **exactly 0** with the target **1183px** below the fold, which reads precisely like a dead anchor. The page is fine — traced frame by frame, every click scrolls when nothing else is animating (`0 → 6 → 25 → 57 → 102` over ~750ms) — so the fix is in the harness: the reset is `window.scrollTo({top: 0, behavior: 'instant'})`, and `CLICK_NAV` settles **before** clicking as well as after. **The old assertion was `sectionTop >= headerBottom - 1`, which a total failure to scroll passes trivially** (1183 >= 190), so this defect was live on the tree that shipped it and nobody saw it. That is the general lesson: a bound phrased as "not worse than" cannot notice "did not happen at all", and the fix was to state the landing position exactly rather than as a bound.
- **Swapping the header background from `--glass` to `--surface-1` moved no contrast, and that is a measurement rather than an assumption — it is in the contrast path and was checked.** **8 of the 193 icons resolve their background to `header.top` itself** (the rest sit on their own button backgrounds), so the swap was genuinely in the compositing path and could have moved 1.4.11 figures. It did not: A/B on the same run, `--glass` and `--surface-1`, both themes, 4 pages — **dark min 3.95 max 7.15, light min 4.27 max 4.70, 0 of 193 below 3:1 in either theme, byte-identical to 2 decimal places**. The reason is arithmetic rather than luck: `--glass` is a translucent layer over `--bg` with **nothing behind the header to blur** — the `backdrop-filter` that was removed with the sticky rule had no subject there, and it was over page background at the top of the page. Probe: `_tmp/probe_icon_after_header.py`. **Do not read "the header is opaque now" as "the header is lighter/darker now":** it is the same colour the glass was already painting. **Superseded the same day** — the panel is gone outright, which is the next bullet; `--surface-1` never shipped as the header's background.
- **The header's panel is gone too, and what it exposed is NOT `--bg`** (partner ruling 2026-09-30: "Подложку в шапке вообще видимо убрать, .top background я полагаю"). `.top` painted `background: var(--surface-1)`, which is not the page colour in either theme — dark `#131315` on `#0a0a0b`, light `#ffffff` on `#f5f6f6` — so the header read as a raised block. Removing the declaration reveals **`body`, which is not flat: it carries a 1px dot grid at 20px** (`background-image: radial-gradient(circle at 1px 1px, var(--dot) 1px, transparent 0)`), and **`.top` was the only paint masking it at the top of the page.** A dot pixel composites to `rgb(22,22,23)` dark and `rgb(228,229,229)` light — in dark, within 3 units of `--surface-1` itself, which is why the panel read as "not much lighter" and why a tolerance-3 pixel match will happily conflate the two.
- **Measured inside the header's OWN box** (`getBoundingClientRect()`, **1225×121** at x=20 y=36, **identical in both arms** — the panel was pure paint, with **zero** layout movement): before, the panel covered **82.74%** dark / **87.08%** light of that box and **0** dot pixels; after, `--bg` is **85.38%** and dots are **0.39%** dark / **0.67%** light. **Light is the bigger visible change**, because `--surface-1` is white there and the dots are grey. Screenshot pairs of both arms in both themes: `_tmp/header_panel_compare_{dark,light}.png`; crop to the element's own rect, never to a fixed height — a fixed 300px crop includes the page below the header and makes every percentage meaningless.
- **Contrast A/B, both arms injected into one run, 4 pages, every icon in the document plus every text element inside the header** (`_tmp/probe_header_nobg.py`): the **8** icons painted directly on the header go **3.95 → 4.02** dark and **4.70 → 4.60** light; the brand `h1` (25.6px/700) **17.44 → 18.6** and **21 → 19.4**. **The 16px text splits into two groups and must be reported as two, because only one of them loses:** the button labels (`RU`, `☀️`/`🌙`, `🌐 RU`) go **5.71 → 5.82** dark and **5.77 → 5.64** light, while the subtitle `p` goes **5.71 → 6.09** dark and **5.77 → 5.33** light — the subtitle is the only thing that loses because it is the only header text sitting on the bare page rather than on a button's `--glass`, which is translucent, so the background walk settles past it. **The worst movement is −0.44:1 and nothing crosses a floor** — the tightest figure anywhere in the header afterwards is **4.60** (icons, light, floor 3:1) and **5.33** (subtitle, light, floor 4.5:1). Light loses because `--surface-1` is white there and `--bg` is not. **The page minimum does not move at all** (dark 3.95, light 4.27, 0 of 193 below 3:1, in both arms), so removing the panel did not weaken anything anywhere else on the page.
- **The dot case is computed, not waved away:** a 1px stroke can land on a 1px dot, so the worst icon on the whole page (`footer .heart`, which is `--signal`) reads **7.15 → 6.54** dark and **4.27 → 3.65** light against a dot instead of flat `--bg`. **That case is not caused by this edit** — it is the footer, and the dots were already the real background everywhere outside the header.
- **`border-bottom` is deliberately KEPT, and that is a separate question rather than part of the ruling.** It is a rule under the header block, `--line` is the project's token for exactly that, and "no panel" is not "no rule". It is one declaration to drop if the partner wants it gone; nothing in any gate objects either way.

- **`.tool-buttons button` is a class that must stay weaker than every rule it contains, and the trap is that "weaker" is not expressible for a descendant selector.** The blanket used to carry `width`/`height` at **(0,1,1)**, which beat every component rule at (0,1,0): `.lang` silently received `.tool-buttons`'s radius, border colour and background instead of its own, and the xs tier's `min-height: var(--tap)` could not reach the burger because Task 9 had raised it to (0,2,0). It now carries **layout only** — `display`, `align-items`, `justify-content`, `flex-shrink: 0`, `font: inherit`, `cursor`, `transition` — and no `width`, `height`, `min-*`, `max-*`, radius, border or paint, because every one of those is a component's business. **The mobile tap floors stay in the `≤767px` block, where `min-width`/`min-height` clamp the used value and therefore beat a higher-specificity `width`/`height` outright** — that is the Stage 3d Task 1 mechanism, and it is why the floors did not have to move into the blanket. **The residual is `.lang`, and it is the one place the prefix matters:** `.tool-buttons .lang` carries `min-width: calc(var(--tap) + var(--space-6))` because a bare `.lang` there is (0,1,0) and loses to the blanket's own `min-*` floor at (0,1,1) in the same block — measured 71.55px instead of 76px, silently, with no other symptom. The `.tool-buttons ` prefix ties the specificity and lets source order settle it. **`.lang` measures 76x40 at ≥768 and 76x44 below; a bare `.lang` measures 44 wide on mobile and the label does not fit its own button.**
- **The header row is four identical squares and one wider labelled button, and that is a requirement, not a coincidence — so a `min-width` shared between two components is a defect even when both are "the same kind of control."** The human partner's rule (2026-09-30): all `.tool-buttons` equal except the language toggle, which may be a little wider because it is the only one carrying a label. The base rule is therefore split by **box, not by paint**: `.lang, .theme-toggle` keeps the shared paint (glass, border, radius, font, letter-spacing, hover), and each gets its own box below it — `.theme-toggle { width: 40px; height: 40px; padding: 0; justify-content: center }` exactly like `.fav-filter`/`.lucky`, and `.lang { min-width: calc(var(--tap) + var(--space-6)); height: 40px; padding: 0 var(--space-3) }`. **What this cost, measured, because it looked free:** the pair rule used to read `min-width: calc(var(--tap) + var(--space-6)); height: 40px; padding: 0 var(--space-3)`, so `.theme-toggle` was **76px wide at ≥768 — the same width as the language toggle** — and only looked right below 768 because the later `≤767` block gave it `min-width: var(--tap)`. Removing the shared `min-width` alone was not enough: with no width of its own, `.theme-toggle` became content-driven and measured **43.59px**, because the shared `padding: 0 var(--space-3)` is 24px around a ~19.6px icon. **A control with no width of its own is content-driven, and "all equal" is therefore not one rule but one explicit box each.** `test_header_controls` is the guard, and it now asserts what the rule says rather than what it happened to do: one shared **height** across `.tool-buttons`, one shared **width** across the icon buttons, `.lang` wider than a square target, and the xs burger at or above 44px. `--logo` was added and then **deleted again** — the partner reverted the 32px logo back to the `width="100" height="100"` attributes on `index.html:70`, so the token is gone and the count is **60 declared / 60 referenced / 0 orphans** today — down from 63 through `--logo` (twice), `--radius-pill` and `--accent-text`. Do not re-add a token for the logo: it is sized by its attributes, and a rule that overrides them is a rule that will be read as load-bearing and then be wrong.
- **`--line-control` is a separate token from `--line` because the two carry different jobs, and 1.4.11 only cares about one of them.** `--line` draws the hairline that separates a card from the page and is allowed to recede; `--line-control` draws the boundary of something you can press and must reach **3:1** against its adjacent background. Measured on the rendered elements in both themes: **3.35:1 dark, 3.07:1 light**, against the 1.50/1.63 the controls were reading before and the 4.34/4.29 of the pre-redesign base. **Do not "simplify" by pointing a control back at `--line`.** `verify.py` 6h reads all **12** control selectors and fails if any stops painting through `--line-control`, and it is the reason this cannot silently regress — the base gate had neither an orphan-token check nor a boundary check, which is how 5 orphans and 12 sub-3:1 borders passed green.
- **The rating colours are brand values in the dark theme and a darker value of the same hue in the light one, and that asymmetry is deliberate.** Measured live: dark KP `#ff5500` **5.79:1** and IMDb `#f6c600` **11.48:1** are the brand hexes verbatim; light uses `#c74000` **5.05:1** and `#8a6d00` **4.92:1** because the brand hexes on white measure **2.96:1** and **1.49:1**. The hue is preserved and AA is bought with value. **A future "make the colours consistent" cleanup that points the light theme at the brand hexes reintroduces an unreadable number** — and the reviewer's own suggested dark `--line-control` `#55565e` (2.6:1) is the same mistake in a different token.

## CRITICAL rules

- Everything that is NOT data validation must stay compatible with a fully static deployment: no server-side logic, no build step. URL parameters are handled client-side via `URLSearchParams` + `history.replaceState`.
- Do NOT break the contract between `data.js`, `i18n.js` and `app.js`:
  - `titleEn` must be Latin script; `titleRu` is the Russian title
  - `desc` is REQUIRED on every record: `desc.ru` and `desc.en`, both non-empty (used for film pages + SEO meta)
  - `genres` values must come only from the keys defined in `I18N.ru.genres` / `I18N.en.genres`
  - any new user-facing string needs keys in BOTH `ru` and `en`
  - if `poster` is set, the file must exist under `static/posters/...webp`
  - poster filenames must match `^[a-z0-9_]+\.webp$` (lowercase, no spaces) and must not collide case-insensitively — `verify.py` block 4a enforces this; dev machines should have `core.ignorecase false` so case-only renames don't slip by git
  - `fav: true` marks a "recommended" item
- `tools/verify.py` is the source of truth for data integrity.
